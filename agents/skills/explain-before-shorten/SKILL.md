# Explain Before Shorten

「短く書く」より先に、「相手に口頭でどう説明するか」を考える。
言葉だけを削るのではなく、その説明で扱う話題を絞って簡潔にする。

## 前提と担当範囲

- 対象の文章と、理解に必要な前後の文脈を読む。図表が説明の一部なら、その内容も確認する。
- 読み手、目的、文体、長さの指定を優先し、会話で共有済みの情報を活用する。
- ファイルの編集や事実確認には、その作業に適したツールを使う。
- 「口頭で説明する」は内容を整理する方法であり、完成文の文体は読み手と目的に合わせる。
- 専門用語は必要に応じて使い、主語は文脈で明らかな場合に省略できる。
- 指示文は、実行する行動が伝わる肯定形を基本にする。禁止・対象外・重要な注意など、否定形で示す必要がある制約には否定形を使う。
- レビューや相談は提案まで。「直して」など編集を依頼されたら、指定された範囲の正本へ反映する。
- 指定された範囲に集中し、関連する箇所だけを変更する。

## 手順

1. **この説明で何を伝えたいかを決める。**
   読み手に理解してほしいことを、一文で整理する。
   仕組みを知る、違いを理解する、手順を実行するなど、文章の役割に合わせる。
   概念説明では仕組みや意味の理解に焦点を当て、採用判断や行動指示は依頼に応じて扱う。
   前後の文脈から目的を読み取り、曖昧さが残る場合はユーザーに確認する。

2. **まず、口頭ならどう説明するかを考える。**
   いったん文字数を脇に置き、読み手が隣にいるつもりで説明を組み立てる。
   「何がどうなるか」「なぜそうなるか」「どんな場合か」を、必要な範囲で具体的にする。
   「分離」「管理」「対応」「保証」などの語を使うときは、実際の動きや条件も具体的に示す。
   事実、推奨、可能性を区別し、原文や確認できた事実に基づいて説明する。

3. **違う話を分け、その場所で必要なものを選ぶ。**
   仕組み、利用条件、例外、注意点を区別する。
   実行時間の制限、必要な設定、通信の待ち時間など、異なる話は文を分けて説明する。
   条件は対応する表のセルや文の近くへ置くなど、どの説明にかかるかを明確にする。
   重複する補足や主題から外れる話は省略・移動を検討する。
   適用条件や重要な制約は本文に残し、読み手がその場で確認できるようにする。
   大きな削除・移動やページ構成の変更が必要なら、依頼範囲を確認する。

4. **意味を保って短くする。**
   重複、不要な前置き、回りくどい修飾を削る。
   主体、動作、因果関係、比較対象、重要な条件を読み取れる状態に保つ。
   「上限数は到達保証ではない」のような独自表現より、意味がそのまま伝わる言い方を選ぶ。
   公式用語は維持し、初出で必要な意味を補足する。
   言葉を削るだけでは収まらない場合は、扱う話題を減らすか構成を見直す。
   文字サイズと略語は読みやすさを保てる範囲にし、読み手がすぐ理解できる表現を選ぶ。

   **肯定形と否定形を使い分ける。**
   読み手にしてほしいことを伝える文は、可能なら「何をするか」が分かる肯定形にする。
   たとえば「設定を忘れないでください」は「設定を確認してください」のように、具体的な行動を示す。
   一方、禁止、危険の回避、例外、利用条件、できないこと、対比を正確に示す文では、否定形を使う。
   たとえば禁止事項の「この機能は使用しないでください」は、禁止の意味を保つため否定形のままにする。
   肯定形に直すと条件や意味の範囲が変わる場合は、否定形を保つ。文の形を変えても、原文の条件・強さ・対象範囲は変えない。

5. **短くした文章だけで伝わるかを確かめる。**
   完成文だけで、何の話で何が起きるかが分かるか確認する。
   隣り合う文を続けて読んで、話題が突然変わらないか、用語の意味が揺れていないか確認する。
   不自然さが残る場合は、単語の置換を繰り返すのではなく、説明の組み立てに戻る。
   短くしたことで意味が失われたら、必要な言葉を戻す。

6. **編集した場合は、保存結果と表示を確認する。**
   ユーザーの既存の変更を保持し、本文・表・図・注記の意味を揃える。
   固定サイズのスライドでは、対応するツールで改行やフッターとの重なりも確認する。
   自動診断に加えて必要なページを実際に見て、表示上の重なりを確認する。
   確認した内容と保存できた範囲を正確に報告する。

## 書き換えの例

| 短くしすぎた表現 | 口頭でも説明しやすい文章 |
| --- | --- |
| 受付と完了確認を分離する | 処理の終了を待たずに受付済みと返し、結果は後から問い合わせる |
| 上限数は到達保証ではない | クォータなどの制約により、表の台数まで増やせない場合がある |
| 上限なしでも中断に備える | 実行時間を無制限にしても、サービス側の更新などで処理が止まることがある |

例文は表現の作り方を示すため、具体的な内容は対象製品や構成の事実に合わせる。
読み手が必要とする技術用語は正確に保ち、意味の伝わる説明を添える。

## 出力

- 通常は完成した文章を先に示し、意味や構成を変えた点だけを短く説明する。
- 編集依頼では正本へ反映し、主な変更を簡潔に報告する。依頼内容が明確なら、そのまま編集を進める。
- 相談やレビューでは、必要なら「伝えたいこと」と書き換え案を示す。未反映なら明記する。
- 通常は完成文と要点を示し、口頭説明用の下書きや検討過程は求められた場合に共有する。

## 不足情報への対応

| 状況 | 対応 |
| --- | --- |
| 原文の意味が複数に取れる | 前後を確認し、曖昧さが残る場合に質問する |
| 技術的な条件を確認できない | 不確かな点を明示し、確認できた事実の範囲で説明する |
| 指定の長さでは条件を保てない | 重要な条件を保てる長さや構成を提示する |
| 表示や保存を確認できない | 文章の改善内容と、表示・保存の確認状況を分けて報告する |

## Post-Run Reflection

最後に、伝えたいことが完成文から読み取れるか、重要な条件が保たれているか、
異なる話題を整理できているか、公式用語と自然な日本語を両立できているかを黙って確認する。
提案と編集の範囲を守り、保存・表示の確認状況を正確に伝えているかも確認する。
ユーザーからの修正は同じ会話で生かすが、依頼なしにスキルや設定へ書き戻さない。
